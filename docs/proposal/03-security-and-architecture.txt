## 9. Cryptographic architecture

### 9.1 Assets and classification

| Class | Examples | Handling |
|---|---|---|
| **A: secrets** | Device key, vault master key, recovery key, passphrase-derived keys | Never leave their protected form; never logged; never in a backup channel in the clear |
| **B: private content** | Titles, notes, kept source excerpts, kept attachments, evidence spans | Encrypted at rest; encrypted in backup; short retention by default |
| **C: schedule metadata** | Due dates, categories, effort, progress | Encrypted at rest and in backup; used for local queries inside the encrypted database |
| **D: low-sensitivity settings** | Theme, text size | Plain local storage is acceptable; may sync with the rest |

### 9.2 What local encryption does and does not buy you

Be honest about this in the documentation; it is where weak security projects over-claim.

- Modern Android already encrypts app-private storage on the device with file-based encryption tied to the user's lock-screen credential [K]. A stolen, locked phone is largely protected by the operating system before your code does anything.
- So app-level encryption mainly adds protection in four situations: (1) **data that leaves the sandbox** (backups, exports, sync); (2) an **app lock** that guards the app when the phone is unlocked and handed to someone; (3) forensic images and debug-bridge extraction where file-based encryption is not the barrier; (4) **tamper evidence** on records.
- It does **not** defend against malware running as root, a compromised operating system, or a malicious accessibility service on an unlocked device. While the app is open and unlocked, plaintext exists in memory. Say so.

### 9.3 Threat model

Attackers and assumptions, then the table.

**In scope:** someone with a copy of a backup or export; someone with a stolen locked phone; ordinary malware with limited permissions; a hostile or compromised storage provider or backend; an attacker with the user's Google account; an attacker with the recovery phrase; a curious developer or operator; accidental leakage through logs, crash reports, notifications; an attacker trying to alter or roll back data without detection.

**Out of scope (documented, not solved):** a fully compromised operating system, hardware attacks on the secure element, physical coercion of the user, and a malicious update delivered through the app store under your own signing identity (partially addressed in 10.4).

| # | Threat | Assets | Attacker capability and surface | Mitigations | Residual risk |
|---|---|---|---|---|---|
| T1 | Attacker obtains a backup or export file | A, B, C | Reads cloud blobs or an exported file; can try offline guessing | Client-side AEAD; random 256-bit keys; passphrase mode uses a memory-hard KDF with strength meter and minimum entropy; opaque file names; bucketed sizes | A weak user-chosen passphrase can be brute-forced offline; file sizes and counts leak activity volume |
| T2 | Stolen locked device | B, C | Physical possession, no unlock | OS file-based encryption; app data wrapped by Keystore keys; auto-lock; excluded from Auto Backup | Device-specific attacks on OS or hardware; bugs outside your control |
| T3 | Malware with limited permissions | B, C (in transit or on screen) | Reads clipboard, overlays, notifications visible to it | No broad storage permission; no plaintext in shared storage; `FLAG_SECURE` on sensitive screens; no secrets on the clipboard; private lock-screen notifications; minimal exported components | Can still read what the user sees on screen if it holds screen-reading privileges; notification content visible to other listeners |
| T4 | Compromised device (root, malicious OS) | all | Full read of process memory and storage | Hardware-backed non-extractable Keystore keys where available; short-lived plaintext; honest statement that this threat is out of scope | Cannot be defended in software; plaintext in memory while unlocked |
| T5 | Malicious or compromised storage backend | B, C, integrity | Can read, delete, replace, replay, reorder blobs | E2EE so contents are opaque; per-record AEAD with associated data binding account, device, sequence; signed manifests; hash chains; rollback checkpoints | Can **delete** data or **withhold** updates (denial of service); can show an old but valid state to a device with no newer reference |
| T6 | Unauthorized access to the user's Google account | C (opaque), availability | Attacker signs in as the user, reads the app data folder | Cloud contents are ciphertext; the key is not derived from Google credentials | Can delete the backup; can see metadata (sizes, times); if the same attacker also has a trusted device or recovery phrase, T12 applies |
| T7 | Stolen authentication session or OAuth token | availability, metadata | Calls Drive API as the user | Minimal scope (`drive.appdata` only [S]); tokens held by the platform account manager, not stored by you; revoke on sign-out | Same as T6 |
| T8 | Malicious or altered backup file presented for restore | integrity, device safety | Crafted file to crash, exhaust memory, or inject records | Verify AEAD and signatures **before** parsing any structure; strict length-prefixed parsing; size and count limits; schema validation; fuzz testing; restore into a staging database, then swap | A valid-but-old backup restores older true data (rollback) unless checkpoints catch it |
| T9 | Developer or operator attempts to read user data | B, C | Has Play Console, build keys, no server | No server holds plaintext or keys in v1; no analytics SDKs; open crypto core for audit | A malicious **app update** could exfiltrate data. Mitigations are partial (10.4) |
| T10 | Accidental exposure via logs, analytics, crash reports, notifications | B, C | Third-party SDKs; verbose logs; lock-screen previews | No third-party analytics or ad SDKs; structured logs with automatic redaction and lint tests that fail on content logging; crash reports optional and scrubbed; lock-screen detail level defaults to hidden | A user choosing to enable previews or crash reports accepts the exposure |
| T11 | Cloud storage account compromise (provider-level) | metadata, availability | Provider-side insider or breach | Same as T5 and T6 | Metadata exposure |
| T12 | Recovery key theft | A, then all | Photographs or steals the written phrase, or malware captures it at display | Show once with explicit save instructions; never store in cleartext; never on the clipboard; warn not to screenshot; optional second factor (passphrase) mode; ability to rotate | Anyone holding the phrase **and** access to the backup can read all data. Rotation limits future exposure only |
| T13 | Silent modification or rollback of records | integrity | Alters or replays old versions of a deadline | Per-record version and hybrid-logical-clock in the AAD; hash-chained device logs; signed manifests; local monotonic checkpoint; visible "last synced from device X" | A brand-new device with no reference cannot prove it got the freshest state; another enrolled device or a compared fingerprint can |

### 9.4 Local storage design

**Database.** Room over **SQLCipher** (page-level encryption of the whole file) [K]. Whole-file encryption means date columns remain indexable and queryable inside the encrypted DB. Field-level encryption would force you to give up queries on dates, which the planner and the Runway need.

**Separate treatment for heavy or optional blobs.** Kept source excerpts and attachments are stored as **separate files** encrypted with their own derived key (Tink AEAD, streaming for large files [K]), so they can have separate retention rules, are never synced unless the user opts in, and can be crypto-erased by deleting a key.

**Settings.** Use DataStore. `EncryptedSharedPreferences` is deprecated, and its own reference warns against backing it up because the key will not exist after restore [S]. For sensitive settings use Tink-based encrypted DataStore if the artifact is stable by implementation time [?], otherwise keep sensitive values inside the encrypted database.

**App lock.** Optional biometric or device-credential gate. Important design caution: if you bind the **only** copy of a key to biometrics, the key can be invalidated when the user enrolls a new fingerprint [K], and the data is gone. Therefore: normal operation uses a hardware-backed key without user-auth binding; "locked mode" adds a second, auth-bound wrap and removes the first; the recovery phrase remains the fallback. Make this a clearly explained choice, not a silent default.

**Memory and screens.** Short-lived plaintext buffers, zeroed where the platform allows (the JVM cannot guarantee this, so claim "reduced exposure," not "erased"). `FLAG_SECURE` on screens showing source text, recovery phrases, and export confirmation, so they do not appear in the recents screenshot.

**Clipboard.** Never put secrets on it. Offer "paste and extract" only on explicit user tap.

**Logging.** A logging wrapper that refuses to accept fields tagged as private content, with unit tests and a lint rule that fails the build if content-bearing types are logged.

### 9.5 Key hierarchy

```
 Android Keystore (hardware-backed where available; StrongBox if present, falling back to TEE)
   |
   +-- Device Key (DK): AES-256-GCM, non-exportable, randomised IV
   |       wraps -->  Vault Master Key (VMK)   [random 256-bit, generated on first run]
   |
 Vault Master Key (VMK)
   |-- HKDF-SHA256(info="db")        -> database key (SQLCipher)
   |-- HKDF-SHA256(info="blob")      -> local blob key (excerpts, attachments)
   |-- HKDF-SHA256(info="fingerprint")-> keyed hash for dismissed-candidate fingerprints
   |-- HKDF-SHA256(info="export")    -> local export wrapping
   |
 Account Root Key (ARK): 256-bit, shared across the user's devices (for backup and sync)
   |-- HKDF(info="record|epoch")     -> per-record keys (see 9.6)
   |-- HKDF(info="manifest-mac")     -> account-level manifest authentication
   |-- wrapped for recovery:  KEK_phrase = HKDF(recovery key)           -> ARK_wrap_phrase
   |-- optionally:            KEK_pass   = Argon2id(passphrase, salt)   -> ARK_wrap_pass
   |-- wrapped per device:    HPKE to the device's public key           -> ARK_wrap_device[i]
```

Every derived key uses a distinct, versioned `info` label (**domain separation**) so a key for one purpose can never be used for another. The same keys are never reused across record types.

In v1 (no sync), the VMK doubles as the ARK. They are separated in the design so that single-device users get the same format as multi-device users, and so migrating to sync is a protocol change, not a data migration.

### 9.6 End-to-end encrypted backup and sync

#### Why E2EE here, in plain words

- **Encryption at rest:** data is encrypted where it is stored. Whoever holds the key (often the same party running the storage) can read it.
- **Transport encryption (TLS):** data is encrypted between your device and a server. The server sees plaintext.
- **End-to-end encryption:** only the user's own devices hold the keys. The storage provider holds opaque blobs. This is the property you want, and the property a server-held master key would destroy.

#### Architecture: Google identity for access, not for keys

- **Sign in with Google** (via the platform credential manager [K]) gives Sibra an *identity* and Drive access.
- **Storage:** the Drive **app data folder** under the `drive.appdata` scope. It is a non-sensitive scope [S], readable only by your app and hidden from the user's Drive interface [S]. It is the user's storage quota, so your marginal cost per user is about zero.
- **No Sibra server in v1.** There is nothing to breach, nothing for you to subpoena, and no ongoing infrastructure cost. The cost is limited push-style sync: you poll on a schedule.
- **Keys are never derived from the Google account.** If Google or an attacker controls the account, they get ciphertext only.
- Abstract the storage behind a `BlobStore` interface so the same protocol can later target a user-chosen folder (via the system file picker), an S3-compatible bucket, or a self-hosted server. Privacy-minded users will ask for that.

#### Data layout

Each device **only writes to its own area** (single-writer logs). That removes write conflicts on a store that lacks atomic compare-and-swap.

```
appDataFolder/
  account.header                 (version, account id, epoch)
  keys/
    ark.wrap.recovery            (ARK wrapped by the recovery key)
    ark.wrap.passphrase          (optional)
    ark.wrap.<deviceId>          (HPKE-wrapped ARK for each enrolled device)
  devices/<deviceId>/
    device.card                  (public keys, label, enrolment time, signed)
    manifest                     (signed list of this device's segments, counters)
    log/<seq>.rec                (encrypted change records, append-only)
    snapshot/<n>.snap            (compacted state; only the owner compacts)
```

File names are opaque (keyed hashes) and record sizes are padded to buckets, reducing metadata leakage.

#### Record format

`version | key id | nonce (24 bytes) | ciphertext | tag`

- **Cipher:** XChaCha20-Poly1305 with random 192-bit nonces [K]. AES-GCM with 96-bit random nonces has a practical limit of about 2^32 messages per key; a record log could approach this over years, and a nonce collision under one key is catastrophic. The extended nonce removes the concern. (Inside the hardware keystore only AES-GCM is available; there, use a **Keystore-generated** randomised IV so the app never chooses nonces itself.)
- **Associated data (AAD):** account id, device id, record id, record version, epoch, sequence number. Moving a ciphertext between records, devices, or epochs makes authentication fail.
- **Per-record key:** `HKDF(ARK, "record" | epoch | record id)`, so one key never encrypts unlimited data.

#### Integrity beyond "AEAD succeeded"

An AEAD stops a hostile store from *altering* a record. It does **not** stop that store from *dropping, replaying, reordering, or truncating*. So:

- Each device's log is a **hash chain**: each record includes the hash of the previous one.
- Each device **signs its manifest** with a key held in Keystore (ECDSA P-256 is the widely supported hardware-backed option [K]; newer curves exist on newer devices but are not universal [K]).
- Manifests are also **MAC'd with an ARK-derived key**, so that a new device which knows only the ARK can still verify account-level authenticity before trusting any device signature.
- Each device keeps a **monotonic checkpoint** (the highest manifest counter it has seen for every device). A store that rolls back or truncates is detected the next time any device that saw the newer state syncs.
- **Residual:** a brand-new device that has never seen a newer state cannot prove freshness. Mitigation: show a short fingerprint of the latest manifest chain that the user can compare across devices, and a visible "last synced from device X at time T." Document this as a known limit of any E2EE sync over an untrusted store.

#### Device enrollment and revocation

- A new device generates its own signing and key-agreement keypairs. It displays a QR code containing its public keys.
- An existing device scans it. Both derive a short authentication code from the key-agreement transcript, and the user confirms they match (defence against a man-in-the-middle).
- The existing device encrypts the ARK to the new device's public key using HPKE (RFC 9180) [K] and uploads `ark.wrap.<deviceId>`.
- **Revocation** bumps the **epoch**: a new ARK is generated, wrapped for the remaining devices and the recovery key, and new records use it. A revoked device keeps whatever it already had and can read old-epoch data it already stored; it cannot decrypt new epochs. State this plainly in the UI.

#### Recovery

- **Default recovery key:** 256 bits of randomness encoded as a 24-word phrase from a standard word list with a checksum [K]. Shown once, with explicit save instructions. Wrong-entry errors are specific (checksum failure vs wrong key).
- **Optional passphrase mode:** for people who prefer a memorised secret. Use **Argon2id**, with parameters calibrated on the device (start from at least the commonly cited minimums, then raise them to a target of a few hundred milliseconds on a mid-range phone) [K, library choice ?]. Enforce a strength meter; the passphrase is the weak link here.
- **Honest consequence:** if the user loses **every** device **and** the recovery phrase (or passphrase), the backup is unrecoverable by design. There is no master key to reset. Say this before the user enables cloud backup, and again in settings.
- No recovery contact or key escrow in v1. Adding one introduces another party who can reconstruct keys and changes the trust story; evaluate later if users demand it.

#### Conflict resolution

- **Per-field last-writer-wins registers** ordered by a **hybrid logical clock**, with deletions as tombstones kept for a minimum retention period. Items are small, independent records (one record per deadline, per milestone), so most concurrent edits merge cleanly.
- **Bound the clock:** reject or flag timestamps far in the future, so a misconfigured or hostile device cannot win every conflict forever.
- **Genuine conflicts** (the same deadline's date changed on two devices) are not silently resolved. Both versions are kept, the item is marked "needs your choice," and the user picks. This follows the product rule that a confirmed deadline never changes silently.

#### Versioning and restore

- Keep periodic **signed snapshots** (for example the last five plus one per week).
- Restore flow: download, verify authentication, parse into a **staging database**, show a diff ("this adds 12 items and changes 3"), then the user confirms and the staging store replaces the live store.
- Duplicate detection on import uses record ids first, then fuzzy matching with a user prompt.

#### Deletion

- Account deletion removes the app data folder content, revokes the token, and wipes local data. Play requires an in-app deletion path and a web deletion link for apps that let users create an account [V]. Because your app has no server, the web page explains the user-side steps (including Drive's "delete hidden app data" option [K]) and the exact data Sibra holds. Confirm with Play review that this satisfies the policy [?].
- Local "delete everything" performs **crypto-erase**: destroy the wrapped keys, then delete files. On flash storage you cannot reliably overwrite data, so deleting the key is the meaningful erasure.

### 9.7 Local export and import

- **Encrypted export file:** magic bytes, format version, KDF parameters, salt, then a **streaming AEAD** (chunked, with the chunk index and final-chunk flag authenticated) so truncation and reordering are detected [K]. Keyed by the recovery key or an export passphrase through Argon2id.
- **Plain exports** (calendar `.ics`, CSV, JSON): behind a warning dialog that says what will be readable by whatever app receives it. Written through the system file picker to a location the user chooses, never into app cache or shared temp.
- **Import:** verify authentication first; parse only authenticated bytes; enforce limits; fuzz the parser.

### 9.8 Android backup channels

- Set `allowBackup="false"`, or explicitly exclude **all** app data from both `cloud-backup` and `device-transfer` in `dataExtractionRules`, and keep `fullBackupContent` for Android 11 and below [S].
- Reason: Keystore keys are not restored onto another device, so restored encrypted files are unreadable garbage, and an automatic cloud copy would sidestep your own backup design [S].
- Product consequence: moving to a new phone requires the in-app restore (recovery phrase or enrolled device). Say so during setup.
- The Block Store API can carry a small token to ease transfer, but it is end-to-end encrypted only "when possible" [S]. Do **not** put keys or secrets in it. A harmless "this account exists" hint is acceptable.

### 9.9 Primitives and libraries

Prefer established libraries; do not implement primitives yourself.

| Purpose | Choice | Notes |
|---|---|---|
| Record AEAD | XChaCha20-Poly1305 (Tink) [K] | 192-bit nonces remove the collision risk of long-lived logs |
| Wrapping inside Keystore | AES-256-GCM (Android Keystore) | Keystore-generated random IV; hardware-backed where available |
| Key derivation | HKDF-SHA256 | Distinct labels per purpose |
| Password-based KDF | Argon2id | Library choice to be verified (a vetted binding or a maintained pure-JVM implementation) [?] |
| Device signatures | ECDSA P-256 in Keystore [K] | Hardware-backed non-exportable; widely supported |
| Key agreement for enrollment | HPKE (RFC 9180) via Tink [K] | Authenticated by a short-code confirmation |
| Streaming exports | Tink streaming AEAD [K] | Authenticates chunk order and end |
| Randomness | `SecureRandom` | Platform CSPRNG |
| Database | SQLCipher via Room [K] | Verify current version, licence, and size at implementation |
| Hashing | SHA-256 | Plain and keyed (HMAC) forms |

### 9.10 Security evidence you will produce

This is what turns "I used encryption" into "I engineered and evaluated a secure system."

1. **Threat model document** (the table above, extended, version-controlled).
2. **Protocol specification** for backup, sync, enrollment, and recovery, written precisely enough that someone else could reimplement it.
3. **Property-based tests** on the pure-Kotlin crypto core: decrypt(encrypt(x)) = x; any bit flip fails authentication; nonces never repeat across a very large simulated run; key derivation domain separation holds.
4. **Adversarial backup tests:** truncation, reordering, record replay, cross-account swaps, rollback, malformed lengths, oversized counts, zip-bomb-style inputs, wrong epoch.
5. **Fuzzing** the record parser and importers (for example with a JVM coverage-guided fuzzer [K]) with corpus and crash logs recorded.
6. **Local privacy tests:** automated checks that no content appears in logs, notifications at default privacy, crash reports, or backups; a test that a full-device-backup attempt yields no usable app data.
7. **OWASP MASVS self-assessment** mapped to test evidence [K]: storage, crypto, auth, network, platform, code, resilience, privacy.
8. **Dependency and supply-chain audit:** pinned and verified dependency checksums, a software bill of materials, a list of every network destination the app can contact, and a policy of no third-party analytics.
9. **A short published security report** that includes defects you found in your own design during testing. Your own working notes say real-defect narratives read as stronger evidence than a flawless story; do the same here.

## 10. Security limitations: what can and cannot be claimed

### 10.1 Who can see what

| Party | Sees plaintext content? | Sees metadata? | Must be trusted for |
|---|---|---|---|
| The user's unlocked phone and Sibra process | Yes, while the app is open | Yes | Everything; this is the trust root |
| Android OS, OEM firmware, Google Play services | Potentially, in principle | Yes | Not being compromised; this is outside your control |
| ML Kit and other on-device components | They process text locally; some models are downloaded by Play services | Model download activity | Closed-source components behaving as documented |
| Google Drive / Google account | **No** (ciphertext only) | Yes: file count, sizes (bucketed), modification times, access times, IP addresses, that this account uses Sibra | Availability; not deleting or withholding data |
| Network observers | No (TLS, and contents are already encrypted) | Destination hosts, timing | none |
| **H-sib (you, the developer)** | **No** in v1: you operate no server and hold no keys | Aggregate Play Console statistics; crash reports only if the user opts in | Not shipping a malicious update (see 10.4) |
| Another app on the device | No, due to the sandbox | Notification text visible to enabled listeners; home-screen widget contents visible to anyone looking | The user's choices about widgets and lock-screen detail |
| Any app or person the user exports or shares to | Yes, whatever is exported | n/a | The user's judgment |

### 10.2 Claims you can honestly make

- "Your deadlines and notes are encrypted on your device and in your backup."
- "Backups are encrypted on your phone before they leave it. The storage provider receives only encrypted data."
- "We run no server that stores your data, so there is nothing on our side to breach."
- "We cannot recover your data if you lose your recovery phrase, by design."
- "Messages are processed on your device and discarded after extraction unless you choose to keep an excerpt."
- "Nothing is read from other apps unless you enable that specific source."

### 10.3 Claims you must not make

- "Unhackable," "military-grade," or "100% secure."
- "Zero-knowledge" as a blanket term. In the strict cryptographic sense it describes proof systems. Marketing use means something looser. If you want a phrase, use "end-to-end encrypted backup, with no server holding your data."
- "The developer cannot read your data" without the qualifier about app updates (10.4).
- Anything implying protection against a compromised phone, a rooted device, or screen-reading malware.
- That notification-access discovery sees all your messages (it sees only what produces a notification).

### 10.4 The malicious-update problem

You control the signed app that users trust. If a future update contained code that uploaded plaintext, architecture alone would not stop it, and Google Play App Signing means a store-signed release is not trivially verifiable by users [K]. Partial mitigations, in increasing order of cost:

1. Publish the **crypto core and the Computus engine** as open source so reviewers can audit the code that handles keys and text.
2. Maintain a **network-destination allowlist** and test that no other host is contacted; publish the list.
3. Publish **reproducible build** instructions where feasible, and release checksums for builds you distribute directly.
4. Keep the privacy dashboard honest: show every network call count since install.

### 10.5 Metadata that remains visible, concretely

- To Google: that the account uses Sibra, when it syncs, approximate data volumes, and device IP addresses at those times.
- Locally: titles on the lock screen if the user turns previews on; widget contents; the order of items in the recents list.
- In logs and crash reports: nothing about content, by policy and by test; the user's opt-in crash reports can still reveal that a particular screen crashed.

## 11. Technical architecture

### 11.1 Decisions and trade-offs

| Decision | Options compared | Choice | Why, and what it costs |
|---|---|---|---|
| UI and platform | Kotlin + Compose, Flutter, React Native, Kotlin Multiplatform with native UI | **Kotlin + Jetpack Compose** | The product lives on Android-specific surfaces (Keystore, alarms, share targets, tile service, widgets, notification styles). A cross-platform layer would add bridge code for most of the value. Costs: Android-only at first. Mitigation: keep the core pure Kotlin so an iOS port is feasible later. |
| Core structure | One module vs. layered modules | **Pure-Kotlin core modules with no Android imports** | Independent unit testing, a command-line evaluation harness that runs the shipped code, and a credible extensibility claim. |
| Persistence | Room + SQLCipher; Room + field-level AEAD; SQLDelight; plain Room | **Room + SQLCipher** (verify current maintenance and size) | Keeps date columns queryable inside encrypted storage. Cost: a native library, APK size, and one more dependency to track. |
| Cryptography | Tink; direct JCA/Keystore; libsodium bindings; BouncyCastle | **Tink + Android Keystore**, plus a vetted Argon2id implementation | Established, maintained, hard to misuse. `EncryptedSharedPreferences` is deprecated, so do not build on it [S]. |
| Reminders | AlarmManager; WorkManager; foreground service | **AlarmManager for time-critical, WorkManager for deferrable, no foreground service** | Matches platform guidance [V]; a foreground service only to keep a notification alive would add policy and battery cost. |
| OCR | ML Kit text recognition; Tesseract; cloud OCR | **ML Kit (Latin) first**, Tesseract later for other scripts | On-device and fast, but five script families only [V]. Cloud OCR is rejected: it would send documents off the device. |
| Document parsing | Heavyweight office libraries; targeted parsers | **PdfRenderer plus a PDF text-layer library; direct ZIP and XML parsing for DOCX and XLSX** with hardening | Office libraries bring large dependency sets that are poorly suited to Android; hand-rolled parsing is small but must disable external XML entities and enforce size, depth, and ratio limits. |
| Extraction | Rules + linear model; transformer; on-device LLM; cloud LLM | **Rules + linear model, ML Kit entity extraction as cross-check, optional later small encoder** | Explainable, tiny, testable. Cloud LLM rejected for privacy. On-device LLM is not available on all devices [S]. |
| Sync storage | Drive app data folder; custom server; Firebase; user-chosen folder | **Drive app data folder behind a `BlobStore` interface** | Zero server cost and no data custody. Cost: no push notifications, scheduled polling, and rate limits to handle. |
| Identity | Sign in with Google (credential manager); email and password; anonymous | **Sign in with Google for identity and Drive access only** | No password handling; no server-side account database. |
| Dependency injection | Hilt; Koin; manual | **Manual constructor injection in core, Hilt in the app shell** | Keeps the core framework-free. |
| Build and supply chain | Default Gradle; verified, pinned | **Version catalog, dependency verification, SBOM, R8** | Evidence for the audit story. |

Minimum SDK suggestion: **API 26** (notification channels, wide device coverage) [K]; compile and target the current required level (API 36 for new releases [S]). Revisit minimum after checking device distribution data.

### 11.3 Performance, battery, and budget phones

- Extraction runs on short text segments; the classifier and tagger are small; no model larger than a few MB at launch.
- OCR is the heavy step: run on demand, cancelable, off the main thread, with image downscaling. Do not OCR in the background.
- Reminders use batched inexact alarms; no timers firing every minute.
- Use baseline profiles and startup benchmarks; set a cold-start budget and test on a low-end device [K].
- Measure battery with a controlled run on real devices and publish the numbers rather than asserting them.

## 12. Data model

Identifiers are time-ordered UUIDs (UUIDv7) [K]. Instants are stored as UTC epoch milliseconds **plus** an IANA zone id **plus** the original local date-time and its precision, because "11:59 PM" in the institution's zone is the real fact, and the device zone can change.

### 12.1 Entities

**Obligation** (the deadline)
- `id`, `title`, `description`
- `kind`: `DEADLINE`, `EVENT`, `OPEN_ENDED` (no fixed date), `RECURRING`
- `due_instant`, `due_zone`, `due_local`, `precision` (`DATE_ONLY`, `DATE_TIME`), `floating` (true if the local time should follow the device zone)
- `category_id`, `importance` (1 to 4), `consequence` (reversible, costly, severe)
- `effort_optimistic`, `effort_likely`, `effort_pessimistic` (minutes)
- `lifecycle`: `ACTIVE`, `COMPLETED`, `CANCELLED`, `ARCHIVED`; `postponed_until`
- `confidence_origin` (extraction confidence at creation), `created_at`, `updated_at`, `hlc`, `deleted_at` (tombstone)
- Urgency state is **derived**, not stored.

**Candidate** (a suggestion awaiting review)
- `id`, proposed fields, `tier` (`SUGGEST`, `MAYBE`), `confidence`, `source_id`
- `relation`: `NEW`, `UPDATE`, `CANCEL`, `DUPLICATE`, `CONFLICT`; `related_obligation_id`
- `status`: `PENDING`, `ACCEPTED`, `DISMISSED`, `SNOOZED`; `snooze_until`; `expires_at` (automatic purge)
- `fingerprint`: keyed hash of normalised title and date, used to avoid re-suggesting dismissed items. Contains no text.

**Source**
- `id`, `type` (`MANUAL`, `SHARE`, `FILE`, `SCAN`, `FEED`, `CALENDAR`, `LMS`, `EMAIL`, `CHAT_EXPORT`, `NOTIFICATION_ACCESS`), `label`, `enabled`, `rules` (allowlist, label filters), `retention_policy`, `last_used_at`. **No message content.**

**Evidence** (optional, user-chosen)
- `id`, `obligation_id`, `blob_ref` (encrypted excerpt or file), `span` (offsets), `retain_until`, `kept_by_user` (always true). Separate encryption key and retention.

**Milestone** and **PlanBlock**
- Milestone: `id`, `obligation_id`, `origin` (`USER`, `SUGGESTED`), `title`, `target_date`, `effort`, `order`, `status`, `depends_on[]`.
- PlanBlock: `id`, `obligation_id`, `milestone_id?`, `day`, `minutes`, `origin`, `status` (`PLANNED`, `DONE`, `SKIPPED`).
- The `origin` field is what lets the UI keep real deadlines and suggestions visually distinct.

**ReminderRule** and **ReminderInstance**
- Rule: `scope` (`GLOBAL`, `CATEGORY`, `OBLIGATION`), `offsets`, `channel`, `intensity`, `quiet_hours`, `repeat`.
- Instance: `id`, `obligation_id`, `kind`, `fire_at`, `state` (`SCHEDULED`, `FIRED`, `SNOOZED`, `CANCELLED`, `MISSED`), `dedupe_key` (unique on obligation, kind, and fire time). The unique key prevents duplicate notifications; the `MISSED` state powers the "you may have missed" ledger.

**Category**, **ObligationLink**, **ChangeLog**
- Category: `id`, `name`, `default_plan_template`, `default_importance`, `default_reminders`.
- Link: `from_id`, `to_id`, `type` (`DEPENDS_ON`, `RELATES_TO`, `UPDATED_BY`).
- ChangeLog: `id`, `obligation_id`, `field`, `old`, `new`, `at`, `actor` (`USER`, `AUTO_RULE`), `reason_code`, `source_id`. This is the audit trail that proves nothing changed silently.

**Sync and device entities**
- DeviceRecord: `device_id`, `public_keys`, `label`, `enrolled_at`, `revoked_at`.
- SyncState: per device `last_seq`, `last_manifest_hash`, `epoch`, `hlc`, the monotonic checkpoint map.
- Tombstone: `record_id`, `deleted_at`, `retain_until`.

**Setting**: key, typed value, `syncs` flag (local-only vs synced).

### 12.2 Relationships

```
Category 1---* Obligation 1---* Milestone 1---* PlanBlock
Obligation 1---* ReminderInstance        Obligation *---* Obligation (ObligationLink)
Obligation 1---* ChangeLog               Obligation 1---0..* Evidence
Source 1---* Candidate *---0..1 Obligation (when relation is UPDATE/CANCEL/DUPLICATE)
ReminderRule scopes: Global | Category | Obligation
```

### 12.3 Sync envelope

Every changed entity is serialised into a `RecordEnvelope { type, id, hlc, device_id, epoch, schema_version, payload }`, then encrypted as in section 9.6. Only the owner device writes its log. Readers merge logs per entity by hybrid logical clock; deletes win over older updates; true concurrent edits to the same field produce a conflict record the user must resolve.

### 12.4 What is intentionally not stored

- Raw messages, full documents, and screenshots, unless the user keeps an excerpt.
- Sender names or contact identities from messages, unless the user keeps that excerpt.
- Anything for sources the user has disabled; disabling a source offers to delete everything that came from it.
